# Kaascan Web App — Build Prompt

## Overview

This document is a **system prompt** / specification for building a **web application** that replicates the Kaascan AI chat experience. It documents every endpoint, auth flow, state architecture, component logic, and simulation pattern extracted from the existing Flutter mobile app (`lib/screens/kaascan_ai.dart`, `lib/Api/client.dart`, `lib/sdk/kaascan_sdk.dart`, and supporting files).

## 2. Authentication Flow

### 2.1 Page Structure

| Page | Purpose |
|------|---------|
| **Login Page** | Phone number input (Rwanda +250) → OTP/PIN entry |
| **Register Page** | Phone number input → Create account → Set PIN |
| **PIN Entry Page** | 4-digit PIN keypad → Biometric fallback |
| **Forgot PIN Flow** | Phone → OTP → New PIN |

### 2.2 API Endpoints

| Method | Endpoint | Purpose |
|--------|----------|---------|
| `GET` | `{BASE_URL}/get-csrf-token` | Get CSRF token (required before all state-changing requests) |
| `POST` | `{BASE_URL}/register/parent` | Register new parent account |
| `POST` | `{BASE_URL}/register/merchant` | Register new merchant account |
| `POST` | `{BASE_URL}/login/parent` | Parent login with phone + PIN/OTP |
| `POST` | `{BASE_URL}/login/merchant` | Merchant login |
| `POST` | `{BASE_URL}/parent/set-pin` | Set 4-digit PIN for parent |
| `POST` | `{BASE_URL}/parent/password-reset/request` | Request PIN reset OTP |
| `POST` | `{BASE_URL}/parent/password-reset/verify` | Verify OTP + set new PIN |

### 2.3 Login Flow (Detailed)

1. User enters phone number (Rwanda format: `078xxxxxxx` → normalize to `0xxxxxxxxx`)
2. App calls `POST /login/parent` with:
   ```json
   {
     "phone_number": "078xxxxxxx",
     "csrf_token": "<from GET /get-csrf-token>",
     "totp_code": null,
     "pin": null
   }
   ```
3. If response `status === "success"`, store `token` (JWT) in localStorage/session
4. Navigate to PIN entry screen
5. On PIN submit, call `POST /login/parent` with `pin` field set
6. On success response `status === "success"`, store JWT token as `login_token` and navigate to Dashboard

### 2.4 Registration Flow

1. User enters phone number
2. Call `POST /register/parent` with:
   ```json
   {
     "phone_number": "078xxxxxxx",
     "csrf_token": "<token>",
     "device_id": "<hashed-device-id>",
     "kcn_token": "<device-ntfy-token>",
     "role": "parent",
     "name": null
   }
   ```
3. Response status can be `"success"` or `"exists"`
4. On success, navigate to PIN setup screen

### 2.5 PIN Setup Flow

1. User enters 4-digit PIN
2. Call `POST /parent/set-pin` with:
   ```json
   {
     "pin": "1234",
     "csrf_token": "<token>"
   }
   ```
   Headers: `Authorization: Bearer <jwt-token>`, `x-csrf-token: <token>`
3. On success, navigate to Dashboard

### 2.6 Token Management

- **JWT Token** stored as `login_token` in localStorage
- **User role** stored as `user_role` (parent/merchant)
- **Has PIN** flag stored as `has_pin`
- **Device ID** generated by hashing device info → stored as `device_id`
- **kcn_token** (ntfy topic) generated by SHA-256 hashing device ID → first 12 chars as topic

### 2.7 Session Expiry Handler

On 401 response from any API call:
1. Clear all localStorage
2. Redirect to login page

### 3.5 Send Message Logic

```
function handleSendMessage(text):
  if (isTypingSend) return  // block if typewriter is animating
  if (text is empty) return
  
  clear input
  addUserMessage(text)
  hapticFeedback()
  
  if (isSimulatedAction):
    // Skip API call — create new bubble with pending data locally
    reset isSimulatedAction
    set isTypingSend = true
    await delay(300ms)
    if (pendingStudentResponse exists):
      create new AI bubble with pendingStudentResponse data
      reset pendingStudentResponse
      set isTypingSend = false
    return
  
  // Normal API call
  try:
    response = await POST /ask { query: text }
    if (response is empty):
      show error
    else:
      addAiResponse(response)
  catch:
    show error
```

### 3.6 Typewriter Effect

When a new AI bubble appears, the text is animated character-by-character:

### 3.7 Agentic Actions (Action Words)

When a response contains `action_word` (e.g., "hano" meaning "here"):

1. The word is highlighted in a different color (yellow/gold) with underline
2. Tapping the word triggers `_handleActionWordTap(actionMessage)`
3. The action depends on context:

| `action_message` prefix | Behavior |
|------------------------|----------|
| `LINK_STUDENT:{id}:{name}:{photoUrl}` | Start linking flow: show welcome message with clickable "guhuza" word |
| `CONFIRM_LINK` | Show confirmation dialog to link student to parent account |
| `NAVIGATE_STUDENTS` | Switch to Students tab |
| Any other string | Typewrite the message and send to AI |

### 3.8 Simulation Flow (Student Cards)

When user taps a student card or action word in a student list:

```
function handleSimulateAndShow(actionMessage, studentResponse):
  // Instead of calling API, locally create and show a new bubble
  isSimulatedAction = true
  pendingStudentResponse = studentResponse
  
  // Typewrite the actionMessage into the input field
  // then auto-send (which triggers simulation branch in handleSendMessage)
  typewriteAndSend(actionMessage)
```

This creates a **local-only** AI bubble with the pre-structured data:
- No network call to `/ask`
- The new bubble contains the welcome message + clickable action words
- For single student: shows "Uyu ni umwana wange" button
- For confirmation: shows the link dialog

### 3.9 Student Linking Flow

```
Step 1: Search student → AI finds student → Shows photo + details + "Uyu ni umwana wange" button

Step 2: Parent taps "Uyu ni umwana wange" (simulated action)
  → New AI bubble: "Nishimiye kuguhuza {name} kuri kaascan..."
  → Contains clickable word "guhuza" (action_message: "CONFIRM_LINK")

Step 3: Parent taps "guhuza" → Confirmation dialog shows:
  - Student photo (large)
  - Student name
  - Warning about linking
  - "Yego, huza" (Yes, link) button

Step 4: On confirm → API call:
  POST /register/student
  Headers: { Authorization: Bearer <jwt>, x-csrf-token: <token> }
  Body: {
    "parent_id": "<from profile>",
    "student_name": "...",
    "student_photo_url": "...",
    "school_name": "",
    "student_pin": "0000",
    "grade": "",
    "csrf_token": "<token>",
    "student_id": "<student_id>"
  }

Step 5: On success → New AI bubble:
  - "Ibi bintu nishimiye kubona wowe numwana wawe mbahuje..."
  - Guide image showing how to set student PIN
  - action_word: "hano" → action_message: "NAVIGATE_STUDENTS"
```

### 3.10 Draggable Student Overlay

When viewing student cards in chat, a **draggable circular photo overlay** appears on top of everything:

- Contains the currently active student's photo + name
- Positioned centered over the app logo initially
- Can be dragged with pan gesture
- Double-tap to dismiss
- Updates as user scrolls through student list cards
- Has close button, drag indicator, and name label

## 5. SDK / Utility Services

### 5.1 Device Token (kcn_token)

Generated once and cached:
1. Get device identifier (Android ID or random UUID)
2. SHA-256 hash the identifier
3. Take first 12 characters as the kcn_token
4. Cache in localStorage

Used for push notifications (ntfy) and device-specific subscriptions.

### 5.2 ntfy Push Notifications

```
Custom server: https://ntfy-z7hbc38dvclzmalytr8ep9du.kaascan.com
Topic: kcn_token (12-character alphabetic)
```

When app starts:
1. Generate/get kcn_token
2. Subscribe to ntfy topic: `wss://ntfy-z7hbc38dvclzmalytr8ep9du.kaascan.com/{kcn_token}/ws`
3. Listen for incoming messages

### 5.3 CSRF Token

Before any state-changing request:
```
GET {BASE_URL}/get-csrf-token
Response: { "csrf_token": "..." }
```

Pass token as:
- Header: `x-csrf-token: <token>`
- Body field: `csrf_token: <token>`

## 7. Error Handling

### 7.1 API Error Handling

```
Try request → catch (DioException):
  - Connection timeout → "Igihe cyarangiye. Ongera ugerageze."
  - Network error → "Nta internet. Reba ko ufite internet wongere ugerageze."
  - 401 → Clear session, redirect to login
  - Any other → "Ntabwo bikunze. Ongera ugerageze nyuma."
```

### 7.2 Chat Error Handling

```
if (API response is empty):
  show AI bubble with error text
  waiting_ask = false

if (API throws):
  show AI bubble with error text
  waiting_ask = false
```

## 11. Key Design Patterns

1. **Structured AI Responses**: The AI doesn't just return text — it returns structured JSON with `status`, `type`, `students[]`, `action_word`, `action_message` etc. The client parses this and renders appropriate UI (student cards, product cards, action buttons).

2. **Local Simulation**: For agentic flows (student linking, navigation), the app uses local simulation (no API call) to create smooth, instant transitions. The `_isSimulatedAction` flag and `_pendingStudentResponse` data enable this pattern.

3. **Typewriter + Staggered Animation**: Text appears character-by-character, and when complete, student cards animate in with staggered delays (each card slightly delayed) creating a polished reveal effect.

4. **Structured Data Extraction**: The chat bubble component parses both the `responseData` prop AND the raw message text as JSON to extract students, products, and action words. This is a dual-path parsing strategy.

5. **Draggable Overlay**: When student cards are visible, a draggable photo overlay floats above all content, updating as the user scrolls through students.
